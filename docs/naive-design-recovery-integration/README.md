# Bounded Naïve design recovery candidate

This is an unapplied increment over the exact `naive-remediation-owner-integration` candidate reviewed at repository commit `ba9f4c417add517ea971502a1d5427b38f767dc9`. It does not adopt application source or deploy anything. Inherited baseline, source and SQL hashes are resolved recursively and checked before this increment is assembled.

The new `naive-design-v1` recovery profile binds an immutable canonical design identity and four task slots: engineer and reviewer, each at revision zero or one. Generic design composition alone mounts the recovery wrapper. Other methods retain their existing recovery restrictions. Pure design, frozen suite and measured cost checkpoints use atomic stage association and current-owner SQL transactions. Exact prior-generation pending associations may rotate their claim token; ambiguous or unassociated claims remain held. Pure artifact associations are bounded to one design, one suite and four costs. External target and judge checkpoints gain no reclaim permission.

Suite and cost keys are generated by trusted canonical core code; the wrapper bounds and pins their associations but is not a model-facing artifact authorization API. Strict generic report recovery uses the retained single report child, and completion checks that child’s settlement. A report or successful behavioral trial does not itself establish settled monetary accounting. Mixed callbacks, native PostgreSQL concurrency, hosted execution and the remaining Naïve plan acceptance gates require their own evidence.

Reproduce a frozen candidate into a previously unused directory:

```sh
python3 docs/naive-design-recovery-integration/assemble.py /tmp/new-design-recovery-stage
python3 docs/naive-design-recovery-integration/verify.py
```

Maintainer finalization, after every worker has finished editing postimages and SQL:

```sh
python3 docs/naive-design-recovery-integration/freeze.py
python3 docs/naive-design-recovery-integration/verify.py \
  --destination /tmp/design-recovery-assembly-one \
  --destination /tmp/design-recovery-assembly-two
```

Choose unused destinations. `freeze.py` verifies the parent manifest and assembler against the reviewed repository commit, assembles that exact dependency graph, captures every inherited source/baseline and SQL namespace path, and writes the incremental manifest and `owner.patch`. The patch includes both source postimages and the two new SQL files. `assemble.py` checks parent dependency pins, inherited preimages and incremental postimages. `verify.py` independently applies the patch to a parent assembly and then checks two fresh assemblies against the complete composed source/SQL hash map. Reproduction copies no credentials.

The new `sql/001-design-stage-recovery.sql` and `sql/002-design-checkpoint-ownership.sql` follow inherited stage ownership/recovery and text integration migrations. Their presence is a review artifact, not evidence of a migration run. All inherited SQL namespaces remain pinned rather than being reapplied as duplicate migrations.

Validation receipts belong in `validation/`. `verification.json` records only completed independent patch and assembly hash checks. Test, typecheck and build receipts are separate integrator evidence; this README asserts no final validation counts. PGlite protocol tests and injected external transports do not establish native PostgreSQL contention or provider acceptance. No provider calls, secrets, customer recruitment, spending, live SQL, source adoption or deployment are authorized by this artifact.
