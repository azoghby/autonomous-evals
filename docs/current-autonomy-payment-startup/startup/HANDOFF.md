# Isolate startup and remaining owner adapter handoff

These source postimages apply only after the exact f88811c artifact on parent 0398517. They replace **artifact-created** current-autonomy runtime, routes and Workflow wrapper; current application source is not overwritten by historical files. The integrator must validate each preimage before generating/applying the patch.

`createCurrentPaymentStartup` consumes a typed `CurrentOwnerAdapters`. The canonical SQL payment bridge replaces owner-supplied request/payment callbacks; quote outbox messages first validate the persisted quote and prepare its actual owner-authenticated `POST /api/jobs/{id}/accept-quote` action. No acceptance is synthesized and no charge is sent. Existing checkout remains responsible for customer acceptance, Stripe session creation, `quote_accepted`, and the existing job Workflow. Per-finding authorization/settlement remains the existing business contract, unsupported by the fixed-quote autonomous protocol.

The runtime imports `loadCurrentAutonomyOwner`, a typed, fail-closed loader handoff. Replace that export with an exact reviewed sibling composition implementing `CurrentOwnerLoader`; do not replace payment/request callbacks, infer source grants, serialize authenticated principals, grant model authority, or fall through to a legacy evaluator. Its `ready.adapters` supplies the retained SQL adapter, finite policy/paid policy, source permission and revocation issuer, genuine pinned provider transport/receipt verifiers, durable operations, metered data/evaluation/recovery/outbox callbacks, current-secret scanner and current request-context dependencies. No secrets or credentials belong in these files. The SQL object must be identical across release and payment bridge so transactions share authoritative state.

Both HTTP entrypoints and `advanceDueJobsStep` resolve the same imported loader inside their own isolate; a prior HTTP `installCurrentAutonomy` call is no longer assumed. Only configuration is cached. Session and canonical ownership are freshly resolved by existing application authorization and the bridge on every call/replay. Scheduler credentials are never serialized into the Workflow. Step retries stay zero; retained operation/payment receipts drive recovery.

Receipt delivery before bootstrap is retained; successful bootstrap re-resolves the owner then drains retained receipts. The bridge's authoritative verification rechecks provider evidence and current quote/payment/tenant/job/environment on access. Production receipt ingestion still requires the separately reviewed current Stripe webhook patch after signature verification, settlement/refund/cancellation persistence, and configured genuine provider receipts. The startup module alone does not activate production, supply those adapters, or claim real hosted Workflow crash/replay verification.

Activation additionally requires an explicit exclusive dispatch-owner decision. The preserved actual webhook still calls `resumeJobForPayment`, which may start the existing job evaluator. The required `exclusiveDispatch(request)` callback is checked before constructing service context and again before evaluation, and must read the durable canonical dispatch owner. The owner must reconcile legacy versus autonomous dispatch and billing writers before enabling autonomous evaluation for the same job; a signed payment alone grants no second evaluation. No activation claim follows from the additive receipt bridge.

Apply `sql/001-current-payment.sql` only through the owner's reviewed migration plan after the release schema. Startup executes no DDL. SQL functions use SECURITY INVOKER and revoke PUBLIC execution; explicit least-privilege server-role grants and actual provider webhook event subscriptions remain genuine configuration gates. The production Stripe adapter obtains secrets through the existing accessor and locally verifies raw signatures with the actual SDK; source contains no secret values. Unbound existing fixed-price/per-finding/subscription webhooks retain their current processing path. Pending receipt draining is bounded before every autonomous scheduler tick, so receipts arriving after bootstrap do not stall indefinitely.
