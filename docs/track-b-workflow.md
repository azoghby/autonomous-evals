# Calendar workflow suite layer

Implementation lives entirely in `packages/core/src/simulator/workflow/index.ts`. Import directly from that folder until the parent wires package exports. No root manifest, existing simulator source, Track A contract, cloud resource, or paid service was changed. These are dependency-injected engine functions, not an independent orchestrator.

## Integration signatures

- `freezeCalendarSuite(input: CalendarSuiteInput): FrozenCalendarSuite`: exactly twelve uniquely identified reviewed scenarios, frozen timestamp, reviewer ID, job ID, and explicit origin (`customer` or `internal_fixture`). Each scenario supplies `{id,prompt,actorId,seed,checks,claimRequiredState?}`. Returns a detached, recursively frozen object with a canonical SHA-256 content hash. Runtime validation rejects unknown fields, malformed seed relationships, populated seed call logs, invalid intervals/zones and invalid state specifications. Claim checks must include exact event identity/fields or matching event fields, rather than counts alone. Every execution revalidates the hash, including after JSON storage/reload.
- `runCalendarSuite({suite,versionLabel,branchId,systemPrompt?,dependencies}): Promise<CalendarWorkflowRun>`: fresh aggregate run identifier plus a fresh simulator scope per scenario. Sequential scenario dispatch stays within the shared transport's two-request limit; the existing runner enforces six rounds. Supply the same frozen suite to each version.
- `investigateCalendarRun({suite,run,dependencies,journal})`: returns `{original,reproductions,pendingScenarioIds,findings}`. Repeats at most three product-failure scenarios, each once. Intent is committed before dispatch. Repeated/concurrent investigation calls reuse recorded evidence; an ambiguous intent stays pending and is never automatically replayed. Infrastructure/inconclusive scenarios do not consume reproduction calls. Confirmation requires the same objective failure reason in the isolated reproduction; missing, changed or unavailable reproduction stays inconclusive.
- `rerunCalendarFinding({suite,run,scenarioId,dependencies,branchId?})`: returns `{original,rerun}` for one selected scenario, under fresh scopes and the original system prompt. Uses the authorized current target provided by the caller. Works after original simulator state is deleted; supply a new authorized branch ID and branch-bound dependencies when needed. Explicit user retests are separate from the automatic three-reproduction investigation bound. Persist this new linked execution rather than replacing original evidence.
- `compareFrozenCalendarRuns(a,b)`: requires matching job, origin, suite hash and scenario membership; returns per-scenario outcomes and normalized event-state comparison. Missing execution evidence yields no state comparison. Returns `statisticalSignificance: 'not_assessed'`; there are no significance, reliability or population claims.
- `toTrackAWorkflowRun(run)`: structurally returns Track A's `{runId,versionLabel,results:[{scenarioId,passed,detail}]}` only when all outcomes are determinate. Throws `workflow_outcome_contract_gap` for infrastructure/inconclusive results. Never turn that exception into failed product checks. Persist the richer run before attempting conversion.

`CalendarWorkflowDependencies` requires a `CalendarSimulator`, its branch-bound `TransactionalDatabase`, and `targetForScenario(scenario): ChatTarget | Promise<ChatTarget>`. Provide a fresh target per scenario and the existing secure transport with shared admission/deadline enforcement. Never supply target credentials to scenario data, the classifier, or findings. The engine does not create connections, authorize branches, provision infrastructure, call Naïve, reserve money or send notifications.

The optional trusted `classifySuccess(execution,scenario)` returns `success`, `no_success` or `unknown`. Supply it through an investigator adapter that actually examines the final response. An absent/failed/invalid classifier or empty final response leaves a requested claim check unknown. `claimRequiredState` describes the claimed action, separately from the scenario's overall safety checks: an unchanged calendar can pass an injected dependency-failure scenario while proving that a claimed booking did not happen. The existing internal buggy/fixed targets exercise this distinction in PostgreSQL tests.

## SQL evidence and partial execution

State checks execute through the existing closed, parameterized SQL grader on a pinned transaction, with the run row locked against simulator writers. Generated SQL is never executed. Exact event fields include owner, time and zone. Findings retain check results and the actual final assistant message, with typed job/branch/suite/scope associations and optional reproduction scope. They preserve whether the originating observation was a product failure, inconclusive or infrastructure error. Nonproduct findings remain inconclusive.

Target errors, simulator errors, SQL grading errors and factory/create/snapshot errors are infrastructure outcomes. Invalid responses and round exhaustion are inconclusive. Successfully completed executions with failed SQL checks are product failures. Unavailable claim assessment is inconclusive unless another objective state check already establishes failure. An injected calendar dependency error is ordinary scenario evidence, not an infrastructure outage of the harness.

Per-scenario exceptions never stop subsequent scenarios, and raw exception strings are not returned (they may contain credentials). Runner-provided partial transcripts/state are retained. If the runner itself throws before returning, the workflow attempts a state snapshot and retains it as `partialState`; it cannot recover the runner's local transcript after an unrecoverable snapshot exception. It does not fabricate evidence, erase prior state, or reset original scopes.

## Persistence and Track A wiring still required

Track A must authorize the job/target/branch association before constructing these dependencies, store the full frozen suite and rich executions/findings, and persist phase outputs before advancing Workflow. An explicit new `runCalendarSuite` invocation intentionally creates a new isolated run; reuse the saved phase result for a retried durable step rather than calling it again. Parent must map engineer-generated `Scenario.input` to `prompt`, validate each `checks[].spec` as a state expectation, and resolve actor/initial fixtures from trusted storage before freeze. Unsupported objective/rubric checks must not be silently dropped. The twelve internal reference scenarios are simulator acceptance fixtures, not engineer-generated customer suites or live provider evidence.

Production `WorkflowInvestigationJournal` must implement `withLock(key,action)`, `load(key)` and `save(key,record)` with cross-process serialization and committed saves before return. Hold logical serialization through dispatch, with suitable durable lock/lease behavior. An ordinary transaction rolled back after an external call is insufficient. `MemoryWorkflowInvestigationJournal` is for local fixtures only. Store original records, including pending attempts, durably across restart. A pending intent requires operator reconciliation; recreating the journal is not permission to retry.

Track A's current boolean-only `RunResult` cannot represent unknown/infrastructure outcomes or carry suite/branch/run evidence associations. Extend that contract and wire the rich results, or explicitly pause handling when conversion throws. Full `EvalServices` wiring, generated-suite review, investigator session provenance, durable result storage/journal implementation, budget reservation, live target validation and cloud lifecycle are parent integration work. This layer makes no live-provider or production-completeness claim. Preserve frozen seed/hash and evidence after branch cleanup; credentials and connection strings belong only in authorized server-side adapters.
