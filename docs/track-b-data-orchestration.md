# Track B durable evaluation-data orchestration

Scope: `packages/core/src/evals/data/**`, this document, and `tests/track-b/data-orchestration/**`. ECC was not enabled. No live provider/search/cloud calls, secret access, spending, outreach, push or PR. No changes to text evaluation, agents, reporting, remediation, app, contracts, manifests, platform or other documentation. This is an implementation sub-agent handoff; no additional child worktrees were created.

Inspected the current data acquisition, quality, answer/expert binding, expert draft/contribution, file/PostgreSQL stores, public discovery/rejection/operation persistence, generation/registry/expert/mapping adapters, PLAN.md, TRACKS.md and existing evaluation-data, public-discovery, adapter and quality-review documentation. The existing pieces already implement bounded acquisition, but previously lacked a single durable bridge between provider completion, independently authenticated review, costs and frozen-suite delivery. The local plan is historical; no remote plan was fetched under the offline constraint.

## Host workflow entry point

`advanceDataOrchestration(spec, initial, context, ports)` executes one bounded step. A's workflow remains the scheduler; there is no background loop. Import through the data index. Keep the task/initial candidate snapshot stable across invocations. Changed task/input identities fail closed in the existing task store. Initial source approvals and answer verification are stripped: imported evidence must pass the authenticated review ledger, including purportedly approved fixtures. Existing sufficient data can become ready after that review without invoking generation.

Composition:

1. Use `createFileEvaluationDataStore` for single-host development or the existing PostgreSQL task store for deployment.
2. Supply `DataOperationLedger`; `createFileDataOperationLedger` is the durable single-host reference implementation (private files, checksum, atomic rename, fsync, atomic ownership, immutable results). The deployment database adapter must implement the same semantics, including current-policy screening and tenant/job isolation. Do not deploy the file adapter to ephemeral/serverless storage.
3. Inject `createMediaWikiDiscovery(...).discover` with its existing durable discovery operation store, bounded public transport and trusted operator queries. No fixture registry is presented as public acquisition. A definitive durable discovery rejection advances to generation without persisting rejected content. Unknown permission is never approval.
4. Inject `createNaiveGenerationAdapter(...)` with the existing durable session runner, enforced session/job caps, and `onMeasuredCost: createDataCostCapture(operations, currentKnownSecrets)`. Generation is candidate-only. Actual generator IDs are preserved, candidates are forcibly synthetic, and provider-supplied verification is discarded. A completed generation operation without a captured measured cost stays pending reconciliation.
5. Use `createAuthenticatedDataReviewLedger({ operations, authenticateHuman, knownSecrets })`. The host's `authenticateHuman(task)` must resolve a human session and authorize the job/task server-side; return null for models and unauthorized sessions. The submit method accepts no principal from candidate/model data. It validates immutable case/source payloads, allows reviewed license determination, checks reviewer identity and writes an immutable receipt plus snapshot index. Its `readReview` is the orchestration port. Qualification/consent and actual factual review remain human responsibilities; use the existing expert helper for contributed data and its consent/contribution bindings. Never auto-compute approvals for unreviewed legacy material.
6. Supply `createDraftOnlyExpertAdapter` with durable private draft storage, or an authorized contribution intake adapter. The draft-only adapter produces `draft_not_sent` with no recipient and returns pending; it is neither acquisition nor outreach. This module has no sender, hiring or payment capability.
7. Supply the existing text design/review/freeze service through `freeze({operationKey, mapping})`. This port must enforce its own text-suite review/admission gates and durable idempotency. The data layer revalidates quality, exports only accepted cases/independently approved exact answers, verifies frozen-suite integrity, and binds job/version/system prompt/exact reference text plus full provenance to the frozen suite digest. It does not edit/refreeze suites or authorize execution.
8. Supply `deliverCost(entry)` as a durable idempotent upsert keyed by taskKey and cost.externalId. Never increment a total on replay. It receives measured cost records, never estimates. Capture precedes delivery; each advance retries delivery, including completed-data replay. Failed delivery blocks ready/freeze. The current capture contract is one immutable measured cost snapshot per generation operation; changed cumulative cost snapshots fail closed and need explicit ledger reconciliation rather than silent replacement.

## Review and permission boundary

The authenticated human receipt binds the complete task and candidate snapshot, and the complete reviewed result. Reusing a receipt for different contents/scope fails closed. Approvals require an explicit approved decision and all candidate case payloads; missing/rejected reviews cannot admit behavioral-only synthetic coverage accidentally. The reviewer must be independent of target, generator and source producer. The quality gate separately enforces answer context digests, exact answer, referenced evidence, allowed uses, content hashes, expert qualification/consent attestations and independence.

The source review fix allows license/permission determination by the trusted reviewer while requiring the original content and retrieval provenance to match exactly. New independent evidence may have new IDs. A changed source under an existing ID never inherits approval. Answer binding includes the reviewed license and source snapshot, so permission edits require new review. The original low-level acquisition API remains available for existing callers; stronger authenticated-receipt orchestration applies when using the new entry point.

## Restart, pending and reconciliation

Provider results are journaled before candidate review and task CAS. A restart during review reloads those results and polls the read-only human ledger, without another provider invocation. CAS losers use the existing task-store checks. Frozen suites and provenance replay after restart without another freeze call. Current secrets supplied through either context or orchestration policy screen inputs, loaded task/operation/review records, costs, mappings and frozen results. Secret values are not placed into the freeze port's mapping payload.

An operation claim is written before invoking a provider or freeze service. Exceptions, explicit pending and lost acknowledgements never authorize an automatic retry. Subsequent advances return `reconciliation_required`; no leases expire. The authorized host reconciler must inspect the original durable provider/session/discovery/freeze ledger, validate the result, and call `operations.complete(key, originalDigest, exactResult, opaqueReceiptId)`. Acquisition results use their original request digest; freeze results contain the verified suite itself. Never manufacture a successful result or retry an ambiguous side effect merely because time passed. An unresolved expert draft is the same pending boundary; authorized intake may reconcile an actual contributed batch later. Replaying an identical terminal completion is allowed; replacing it fails. Stale file locks require operator inspection, never timer deletion.

Review reads are safe to poll because they perform no external effect. Immutable two-record review intake writes can be replayed with the identical receipt after a crash. Concurrent file operations fail busy rather than silently dispatching a second effect. Deployments should retry storage contention through their workflow policy, with the same task/request IDs.

Progress is a fixed-prose projection with ready/inconclusive outcome. Provider errors, source content, reviewer identities and costs are not copied into chat prose. `ready` means reviewed data mapped to a frozen suite; it does not mean the target passed evaluation. Full task and provenance are private artifacts for authorized adapters, not safe chat payloads. The host owns opaque evidence references and access control.
