# Backend artifact boundary

`structured-progress.patch` modifies only the private app composition and adds two server modules when applied. It is generated by `python3 docs/structured-progress-integration/backend/build-patch.py`. The patch expects the prior `docs/progress-chat-integration/combined.patch` first and the explicit Track B core prerequisite documented in the parent handoff. Apply `001-structured-progress.sql` separately through the owner's migration process. This directory itself changes no application source and performs no migration.

`readStructuredProgress` must run inside the existing authorized pinned read-only repeatable-read transaction, after current credential policy is loaded. Its access closure is backed by that outer authorization, including the existing operator rule. The inventory owner is always the job's customer, while private chat/HMAC scope is the authenticated subject plus job. Package/environment and inventory revision are rechecked in the same SQL snapshot. Trace Audit returns to the existing adapter; every structured package requires durable planned identities. Missing inventory raises the existing fixed safe invalid-snapshot error, with no Trace-only or clean fallback.

The actual read-only get methods of `PostgresTextCheckpointStore` and `createPostgresEvaluationDataStore` consume the same pinned SQL executor. Their write transaction member deliberately rejects invocation; no claim/CAS/provider/retry method is exposed to the reader. Planned missing checkpoints and evaluation-data tasks are passed to core as missing, preserving input/provider blockers. Current secret screening applies both during acquisition decoding and projection, and the existing chat service continues screening replay/history/poll output.

The final snapshot retains structured findings only from the core projection, original app state blockers, and the complete bounded app cost ledger. App costs can be `naive` or `ai_gateway`; core projection costs accept only measured `naive_session`. Therefore the core projection's cost channel is empty/unknown and the app's already validated costs are merged within the same pinned transaction. No app row is fabricated as a measured provider entry. Ledger truncation still fails using existing adapter bounds; completeness remains unknown, including at delivery.

The stored inventory `observed_at` is the progress watermark. It is never replaced by request time, job update time, or an unrelated event. Newer job/event/cost material rejects the structured snapshot until the producer republishes. Core validates included task/checkpoint timestamps against that watermark. Checkpoint tables have no modification timestamp: the composition owner MUST atomically touch/publish inventory with every included evidence mutation. Otherwise pending-to-completed Calendar changes cannot independently prove when they were observed. This is a producer prerequisite, not a guarantee supplied by a read-only adapter.

`publishStructuredInventory` is a server-only Workflow composition helper, with no HTTP route. Call it in a pinned write transaction with trusted authorized tenant/job/environment, the last read revision (or null initially), and typed planned associations. It locks the owning job and inventory, rejects cross-scope/environment/package keys and actual digest conflicts, preserves all frozen existing associations, appends new identities, and stores a monotonic SQL timestamp plus incremented revision. Its transaction must roll back if anything throws. Missing rows are allowed for independently known expected work; trusted planning MUST generate the exact canonical keys used by the rich factories. Calendar engine run/scenario execution IDs are issued during dispatch: a complete run association containing the actual returned engine runId cannot be published before that result exists. The owner needs an additional durable planned-operation/claim association and final actual-result binding, or an explicit operation-specific inventory format extension, to cover that dispatch interval. Do not insert placeholder run IDs or mutate a frozen association to simulate it. Acquisition/design inventory can cover predispatch blockers; completed Calendar run/investigation entries bind actual returned identities. JSON supplied by a customer/provider is never an identity authority. No replacement of an association is permitted under an existing key; a new operation needs a new identity.

The current Track A Workflow invokes legacy `EvalServices`, whose core compose methods for design/run/investigate are unavailable. It does not invoke this publisher or the rich factories. Parent `PREREQUISITES.md` gives exact missing composition steps and canonical identity sources. This artifact cannot make those producers exist or turn their absence into successful progress. Do not enable structured chat until that owner work and the parent core findings/report-basis fixes are integrated and tested. Literal 12-scenario rich engine scope remains separate from the Track A appended 32-scenario pack; the latter is unknown until explicitly associated and verified.
