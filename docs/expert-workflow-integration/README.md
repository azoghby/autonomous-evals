# Expert Workflow acquisition mount (owner review artifact)

`source/` and `owner.patch` propose a current-base application mount; actual Track A files are unchanged. Regenerate with `python3 docs/expert-workflow-integration/build-artifact.py`. `manifest.json` records exact preimages and postimages; `SUPPORT-PINS.json` separately pins the required current core orchestration/response support by SHA-256 (resume ports are newer than the patch base). Apply only together with the hardened combined expert/cost adoption artifact and current core data support (including explicit durable generation/freeze resume ports). No migration, dispatch, provider activation or deployment has been performed.

The actual `jobWorkflow` now checks an owner-provisioned `expert_workflow.plans` row for `text_eval` before discarding partial state or beginning legacy evaluation. No plan retains the existing branch. A disabled/revoked plan cannot fall through to legacy. An enabled plan advances the existing `advanceDataOrchestration` implementation, SQL task/operation stores, bounded MediaWiki discovery, durable Naïve candidate generation, the real expert owner adapter, private questionnaire response extraction, authenticated independent review and text design/freeze gates. No second evaluator, billing pipeline or arbitrary URL discovery provider is introduced.

The task and initial corpus come from immutable operator-owned SQL records bound to the canonical job/customer, with a digest, trusted generic topic, enabled flag and fixed seven-day response deadline. No endpoint or model grants these records. Real acquisition refuses before runtime construction unless `EVAL_SERVICES=real`. Provider calls and private publication recheck plan/job authority and current secrets; expert dispatch uses the hardened owner's async secret/authority callback. Stable canonical job budget caps are retained; each runner call refuses when its requested cap exceeds current remaining allowance. Cost delivery uses the existing idempotent application sink and retained outbox.

The expert adapter receives the same deterministic operation identity on every poll. Pending expert, generation and freeze effects advance only through explicit provider-owned resume callbacks: Naïve generation and text design use the existing SQL-fenced AgentSessionService and stable task identities. Time does not permit a new attempt or resend. Independent contribution reviews bind exact extraction snapshots and authenticated operator customer IDs. `reviewExpertWorkflowContribution` and `reviewExpertWorkflowData` expose server-only authenticated intake helpers; no new public review route or model approval authority is installed.

While pending, the existing Workflow remains alive using at most 336 durable thirty-minute timer polls, bounded additionally by the persisted deadline. It races a single retained event read against a single retained timer, so cancellation is handled promptly and irrelevant events do not create competing hook reads or extend the deadline. At expiry, revocation or infrastructure/reconciliation failure it retains an explicit pending customer outcome; it never enters the failed-job, report delivery or settlement path. Ordinary responses arriving hours later are picked up by the same Workflow, without a manual restart.

**Remaining execution prerequisite:** current `services.designSuite` returns a legacy suite and cannot consume a bound `FrozenTextSuite` with rich rubric/inconclusive results. Current real composition still marks rich design/run/investigation unavailable and otherwise falls back to lite. This artifact deliberately holds even a fully reviewed frozen result as `ready_consumer_required`/`on_hold`. Adoption of the canonical rich execution/report consumer is still required before automatic evaluation resumption can be claimed. No fake boolean rubric mapping or fallback is used. Sandbox Workflow behavior is preserved.

Owner adoption also requires canonical data-persistence/discovery/review SQL and the expert budget schema, trusted policy/qualification/use grants, and registration of the new `expert_workflow` SQL sidecar migration with the owning migration process. The standalone SQL postimage does not fabricate Drizzle journal/snapshot metadata or apply itself. The current core `buildAgentDeps` factory is exported by a one-line postimage so this mount reuses the existing runtime. No environment files or secret values are included.

Validation: 12 focused tests exercise the actual mounted Workflow and producer with fake dependencies only; full web TypeScript passes and Next Workflow typegen compiles 55 steps and 4 workflows in `/tmp/expert-workflow-mount-stage`. See `tests/README.md`. This proves local control-flow behavior, not real email delivery, customer responses, deployed timers, payout, or a working rich execution consumer.
