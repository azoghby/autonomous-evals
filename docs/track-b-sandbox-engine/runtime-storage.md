# Durable retained SQL runtime storage

This addition owns only `evals/sandbox/runtime-storage/**`, its matching Track B tests, and this document. It exports `createPostgresRuntimeStorage` and `createDurableRuntimeSnapshots` from its own index; application/integration indexes, runtime bridge, persistence, Track A and application migrations remain unchanged. The SQL migration here is an optional artifact, never applied to an external database by this work. This is local PostgreSQL durability and actual PGlite recovery, with no hosted acceptance claim.

## Exact integration handoff

A trusted server composition creates the PostgreSQL repository with its connection-pinned `AgentTransactionalSql`, immutable `{tenantId,jobId,environmentId}`, `authorize({scope,operation})`, `knownSecrets()` and `screenImage(bytes,secrets)`. Transactions must use READ COMMITTED or stronger isolation, roll back on error, commit before resolving, and never automatically retry callbacks. Install `runtime-storage/migration.sql` through the owning application's reviewed migration process before use. All SQL identifiers are fixed and values bound. Keep the repository and raw SQL credential private to server code.

`knownSecrets()` must resolve current and retired credentials covering the entire retention period in every process. `screenImage` is a mandatory trusted complete-image policy: compressed PGlite dumps cannot be made secret-free by scanning their UTF-8 bytes. The owner must independently inspect/reject forbidden image content or enforce a reviewed image policy with equivalent coverage. A no-op callback is only suitable for known-secret-free local fixtures, and is not a production implementation. Metadata and SQL results are additionally screened with fresh secret configuration. Digests protect consistency; they do not authenticate a compromised database or an untrusted callback.

Create `createDurableRuntimeSnapshots({storage,resolvePolicy,maxRows?,maxImageBytes?,synchronousReadGuard?})`. `resolvePolicy(binding)` is an authorized trusted **durable lookup** of an independently issued policy, not an issuance API. Its policy must already have been issued before that run executes, without observing actual changes. Supply null when authority is unavailable; recovery never converts actual rows, samples, a successful SQL predicate, or a matching digest into permission. Lookup must return the exact `ExactRowPolicy`, including run/world/execution/scenario/env/suite/all versions, or null. Both publication and recovery compare this durable record. Policy issuer authenticity, issuance ordering, environment admission and execution digest construction remain the integration owner's responsibilities.

1. Allocate the actual run privately, preserve its original identity and construct the exact `PolicyRequest`. Call `prepare(binding)` before tools execute. It detaches binding and policy. Route operations through the existing bridge's quiescing wrapper, keeping raw SQL/runtime private.
2. In the bridge's capture hook, after accepted operations drain and actual `raw.diff()` refreshes `sandbox_diff`, publish using the prepared handle's `publish(owningSqlImageSource,{diff,toolCalls,outbox})`. The receipts must come from the same quiescent run. The source must export the **entire actual** PGlite data directory. No summary or fixture reconstruction is supported. Dispose the raw run only after capture has completed or failed. Capture failure is not permission to resubmit changed bytes under this identity.
3. The publication result contains the exact image digest/size, detached receipts and policy and the same content-derived snapshot ID as the runtime bridge (`request,image,diff,calls,outbox`). The bridge capture hook must return a `RetainedSqlImage` constructed from the **same persisted bytes**: read `saved = await storage.get(binding)`, require a non-null result, then call `capturePGliteImage({dumpDataDir: async () => new Blob([Uint8Array.from(saved.bytes).buffer])})` and verify its digest equals the publication result. Do not dump the live database a second time: a second archive can differ and produce another snapshot ID. This durable adapter is the restart authority. Composition must compare returned receipts to the execution artifact exactly as the bridge does before grading. This module does not invent a world registry or wire `finalSnapshot` for foreign artifacts.
4. On restart, call `recover(binding)` with that exact trusted binding. It verifies immutable metadata and bytes, checks current authorization and durable policy, loads an independent actual read-only PGlite database and reconciles the full fixed `ROW_DIFF_SQL` relation against summary counts. Missing rows return null; corrupt, reaped, conflicting, unauthorized or unavailable records reject. It never substitutes an empty world.
5. Grade with the returned `snapshot.run` and `snapshot.evidence`; preserve its completeness and authority fields. Always `release()` the returned independent database. Reads use A's SQL validator, bound parameters, READ ONLY transactions, rollback and statement timeout. Limits reject oversized output instead of truncating and falsely claiming completeness. Default maxRows is 5000; the database still materializes query results, so production memory/CPU isolation is a separate owner gate.

`trajectory()` is a legacy synchronous interface. To support it, supply `synchronousReadGuard(calls)` that synchronously verifies **current ownership and current/retired-secret policy**, returning exactly true. Without it trajectory fails closed, and trajectory-dependent grades remain unknown. The guard receives detached data and cannot change the returned receipt. Async query and diff operations use the repository's fresh async authorization. Evidence returned to trusted server code is a detached receipt, not a transferable capability bypassing authorization.

## Atomicity, retention and failure handling

Image bytes, metadata, identity and digests publish in one PostgreSQL row transaction. Scope plus original run ID is unique: a changed world, execution, version, policy, digest, size or receipt conflicts rather than opening another namespace. Identical publication is idempotent across separate connections. If commit acknowledgement is lost, recover/get the exact binding or retry `storage.put` with the **same retained bytes and record**. A prepared handle memoizes its capture, including failure, so retries do not take a second snapshot of a potentially changed live run. Restart without the original bytes must reconcile via get/recover, not rerun effects or recapture another run.

Every new image is `needed=true` with no automatic expiry. `retain(binding,untilEpochMs)` marks it needed and monotonically extends its retention deadline. `releaseRetention(binding)` is an explicit trusted lifecycle-owner decision that no future recovery needs this image; the owner must never release a still-running, pending-publication, report-retained or otherwise needed run. A repeated release remains a release decision, so only one coordinated lifecycle owner may issue it. `reap(nowEpochMs)` affects only this authorized scope, only explicitly released images and only expired deadlines. Each reaper call processes at most 100 eligible rows using locked batches with SKIP LOCKED. It atomically clears image bytes and retains an immutable tombstone. Reaped run IDs cannot be reused, rebound or silently resurrected.

Reads copy and validate image bytes under a row lock before returning; independent PGlite leases contain their own bytes. A later authorized reap cannot delete an open database's image. Competing retain/release/reap/publication operations serialize through PostgreSQL row locks. The injected trusted reaper clock and lifecycle release authorization are server responsibilities. Tombstone metadata remains private and is not itself removed by this reaper.

Default image limit is 64 MiB (hard maximum 256 MiB); default metadata limit is 4 MB (maximum 16 MB). Full binary images may contain private SQL state; they require owner-only database/storage access, an appropriate secret policy and infrastructure resource isolation. No network/provider/cloud access, dependency installation, external migration, deployment or push is required.
