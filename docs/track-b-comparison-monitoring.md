# Track B rich comparison and monitoring composition

This is an additive, **unwired Track B service**, not a deployed monitoring product. `createComparisonMonitoringService` in `packages/core/src/monitoring` composes existing frozen text/calendar execution and investigation services. It does not change the shared app contracts, schedule work, deliver email, call providers directly, or claim statistical significance. Acceptance evidence uses explicitly labeled local fixtures; measured fixture amounts are not actual provider spend.

## Boundary and adapter

Call `service.compare(ctx, { operationId, baselineVersion, currentVersion, mode })` with a stable operation ID per comparison or monitoring tick. The trusted `resolve(ctx, request)` must authenticate the caller and return `AuthorizedComparison`: tenant, job, environment, fixture label, exact reviewed frozen suite, **complete application scenario inventory**, and two authorized version bindings. Each binding identifies the target configuration and simulator branch and supplies a `RichEvaluationAdapter`. Resolve authorization on every replay; credentials never enter this result. Version identifiers are opaque nonsecret IDs and must change with endpoint/model/prompt/config changes.

Use `createTextComparisonAdapter({ services, ctx, suiteDigest, readCosts })` and `createCalendarComparisonAdapter({ services, ctx, suiteId, readCosts })` with already configured `createTextEvaluationServices` / `createCalendarEvaluationServices` instances. Each adapter reads a previously frozen suite, runs the existing engine, invokes its investigator, and retains its complete rich report input. No duplicate evaluation engine or investigator is introduced. The text suite's prompt and `versionLabel` remain frozen; baseline/current target identities are separate binding fields. Comparing different system prompts by mutating the suite is unsupported. Calendar branches must be authorized by the application's resolver; scenario state IDs and top-level runs must be distinct.

For monitoring, bind the original retained rich artifact with `createRetainedComparisonAdapter(originalArtifact)` as the baseline and an execution adapter as current. Monitoring rejects a baseline adapter without `readOnly: true`. The application must load the original artifact under the same tenant/job/target/branch authorization. Each nightly tick gets a stable new operation ID; concurrent dispatchers for that tick use the SAME ID. Baseline evidence is copied and never modified. The execution adapter's service context must be scoped to the same authorized job/environment as the composition context; this association is part of the trusted resolver contract.

`readCosts(operationId)` reads provider-reported cost ledger entries, scoped to this execution, as `{ costs: [{ id, source, microUsd, measured: true }], unknownCosts: [...] }`. Source plus provider operation ID deduplicates costs; conflicting duplicates and unsafe/noninteger amounts fail closed. Returning no entries means zero **known** cost, never free execution. Hosting and customer provider usage remain explicitly unknown; other unmeasured provider/judge usage must be included by the ledger adapter. The composition does not call `recordCost` again or infer profit; existing engines retain responsibility for settling actual spend. Account for suite design and any retained baseline costs explicitly when presenting incremental monitoring versus total job cost.

## Durability and outcomes

Supply the real `PostgresTextCheckpointStore` with `evals/integration/migrations/001-text-integration.sql` installed in the durable application database. Existing ports support this without schema or manifest changes. The composition commits immutable request/tenant/job/environment/suite/target/branch identity before dispatch; commits a nonexpiring claim separately for each version; and stores the entire completed artifact before advancing. Baseline completion survives a current-version failure. Restart/replay returns retained artifacts without reissuing target calls. Changed identity under the same operation ID is rejected. A pending/lost worker or ambiguous target outcome requires operator reconciliation; claims are never automatically released or expired. Availability is deliberately limited after ambiguous failures. There is no new public reconciliation endpoint.

The response retains both full suites/runs, investigations and limitations, grounded check references, fixture label, measured cost entries and unknowns. It distinguishes `passed`, objective `failed`, `rubric_concern`, `not_assessed`, `inconclusive`, `infrastructure_error`, and `check_error`. Subjective failure is not promoted to objective regression. Missing or extra scenario/check identities, reused run/state IDs, mismatched suites/branches, or missing definitive calendar execution/state-grade evidence are refused. Known credentials and invalid JSON text are screened before persistence and return; raw artifacts remain private evidence and require escaped, authorized rendering downstream.

A regression means only pass-to-objective-fail; an improvement means fail-to-pass. Every nonbinary pair remains unresolved. Counts enumerate all outcomes, and `passRateDelta` is the current minus baseline pass fraction **only over the same pairs assessed on both sides**, or null when there are none. `changes` also retains nonbinary outcome transitions. Calendar state differences reuse `compareFrozenCalendarRuns`. Alerts are generic drafts for changed or unresolved monitoring results; they never contain customer response text or deliver messages. These are observed differences on twelve scenarios, not reliability or statistical significance claims.

## Track A integration gates

Read-only inspection used local `origin/track-a` commit `f0068733ca49c37f40fd7de279325f21a4b5fbbb`. Its `EvalServices.RunResult` is boolean and cannot represent these outcomes. Its comparison workflow rewrites suite version labels; its monitoring path uses `!passed` and dispatches before the unique daily record is inserted. None of those paths is silently wired into this service.

Track A appends a red-team pack before persisting its suite. Both frozen engines currently require exactly twelve reviewed scenarios. The required complete `scenarioIds` inventory must include appended cases; mismatches fail **before either version runs**. Do not omit appended results, truncate the inventory, or advertise pack coverage. An agreed reviewed/frozen pack execution and evidence contract is needed before this adapter can process those jobs. Until then the service supports only explicitly scoped frozen twelve-case jobs and refuses augmented application jobs.

Remaining application work: agree the rich shared contract; load and authorize immutable artifacts and all target/branch associations; pass the full scenario inventory; connect durable SQL, private artifact storage and measured cost ledgers; enforce subscription/payment/budget/credential/endpoint policy; persist stable per-tick operation IDs before external dispatch; implement operator reconciliation; render all rich outcomes and evidence safely; wire authenticated Cron, notifications and delivery idempotency; verify production restart/concurrency/access controls. Cleanup must retain exported evidence and recreate fresh simulator state for later runs after branch deletion. No deployment, provider, billing, email or live-cost verification was performed here.

### Retained monitoring identity

`createRetainedComparisonAdapter` supplies a canonical full-artifact SHA-256 digest and run ID through `retainedIdentity`. Custom read-only adapters must supply the same immutable binding. Changing evidence under the same operation ID fails closed, even if the run ID is unchanged. Use a new monitoring tick for an intentional baseline update. Old checkpoint bindings require reconciliation; do not overwrite them. Calendar verdicts are checked against execution stops, exact frozen SQL checks and aggregate/claim grades before comparison.
