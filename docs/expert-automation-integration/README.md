# Automated expert owner integration (review artifact)

Pinned to main `eaf7f6967f0d227b9826232afa9c368a2464e1be`. Actual Track A files are unchanged. `source/` is the editable overlay; `postimages/`, `owner.patch`, and `manifest.json` are regenerated with `python3 docs/expert-automation-integration/build-owner-artifact.py`. Applying the patch is a separate owner action. No migration, email, commitment, provider operation or payment was executed by producing this artifact.

`createSqlExpertOwner(sql, options)` binds the existing bounded core expert adapter to actual expert requests, expert profiles, private questionnaire engagements, and founder outreach drafts. `createOwnerExpertStep` returns the bounded function for the existing acquisition Workflow to call initially and on explicit expert reconciliation. It does not create another evaluator or scheduler. The required response port supplies authenticated independently reviewed contribution snapshots; merely receiving an answer never establishes factual truth.

Owner adoption requires the current application migrations (through0022), the existing `text_integration.checkpoints` migration used by the core CAS store, and adoption of the separately pinned Track B `expert-response.ts` support module (see test SUPPORT-PINS.json), and a shared `BudgetLedger` with the durable Postgres budget schema. The separate cost owner artifact proposes0023; this artifact uses0024 to avoid that numbering conflict. Apply0024 through the owner's migration process and add its generated Drizzle journal metadata there; this standalone SQL review artifact intentionally does not fabricate a journal entry or autoapply a migration. The same durable shared ledger must serve all expert promises. Supply `options.ledger(tx)` as a transaction-bound ledger factory, for example a PostgresBudgetLedger with `{query: tx.query.bind(tx), transaction: fn => fn(tx)}`; never start a nested transaction or use a separate connection for the reservation. The additional SQL sums conservatively retain every unresolved bridge promise; they do not replace the shared expert-job and expert-company-day ledger scopes.

A trusted owner must provision enabled `expert_automation_policies` (exact $25 evaluation / $50 company UTC day caps), `expert_automation_scopes` binding actual `jobs.customer_id`, task, request hash, safe generic topic and current customer-sharing consent, and `expert_automation_qualifications` with evidence, allowed uses and consent receipt. No public form, model response or supplied email can grant these records. Existing opt-in status plus `contactForPaidWork` authorizes standing contact only for qualified unsuppressed profiles. Customer-nominated and researched profiles enter actual pending founder drafts. A managed draft is intercepted by the existing approval route: authenticated `isOperator` approval records the actual operator, and the Workflow subsequently reserves and sends through the durable owner boundary. Legacy direct sending is bypassed for managed drafts.

Operations retain one immutable request UUID and the first promise day. Invitation creation and request questionnaire updates are transactional; tokens are hashed using the existing SHA-256 format and raw tokens remain private in the existing draft body. Promise amounts remain held until explicit owner reconciliation; there is no automatic payout or automatic release. Dispatch claims persist before calling the existing `sendEmail` transport (injected only in tests). Transport or receipt persistence failures retain the claim and return ambiguous. Recovery only reads durable state and cannot retry a send. Recipient suppression, current qualification, standing/founder authority and sharing consent are rechecked at the claim boundary.

Configure `appUrl` and `companyAddress` from trusted owner configuration; cold outreach requires the actual configured mailing address. Generic topics and private customer questions remain subject to the core safety/consent gate. Existing questionnaire constraints are enforced: at most eight questions of at most1000 characters. Unsupported larger requests remain blocked rather than silently truncating questions.

Tests use applied postimages and fake email only; they do not prove hosted delivery, real expert review, automatic payouts, or deployment. See the separate test runner and captured verification produced by the parent integrator.

Legacy and managed founder approvals share the advisory writer lock in the outreach postimage. The legacy transport call runs while this writer gate is held, so a slow mail provider can delay concurrent founder approvals. Hosted multi-connection acceptance remains required.
